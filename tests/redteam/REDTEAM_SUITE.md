# Red-team suite

**Rule:** a test *passes* when the attack *fails*. CI (the `redteam` job in `ci.yml`) runs every test marked
`CI` on a rootless-Podman GitHub runner with the mock inference backend; tests marked `GPU` will
run locally via `make redteam-gpu` (not built yet: it fails until M3). Any attack success fails
the job. No test may be skipped without a tracked issue number and an expiry date in the skip
reason; review enforces this (no CI step reads skip reasons yet).

## Harness

- Each row's test is a Rust test named `rt_<category>_<nn>_…` after its ID (category in lower
  case, the number and any letter as in the ID: RT-SEC-06b is `rt_sec_06b_…`), in the crate that
  owns the defence, as an integration test under `crates/<crate>/tests/` or a unit test under
  `crates/<crate>/src/`. The `tests/` files include ones that start no container, for example
  `crates/sally-core/tests/rt_manifest.rs`, `crates/sally-cli/tests/audit_cli.rs` and
  `crates/sallyd/tests/scan.rs`. Each row's **Test** column names every file that holds a
  function with its prefix: the `tests/` files first, then the `src/` files, each group in byte
  order of the full path (`crates/sally-cli/…` before `crates/sally-core/…` before
  `crates/sallyd/…`); "none yet" means the row lands in a later milestone (its M column).
  `make redteam` runs every test whose name starts `rt_` (`REDTEAM_FILTER` in the `Makefile`)
  with cargo-nextest, and fails when cgroup v2 is missing or nothing is selected.
- **Fixtures** are built in code, not read from files. `crates/sallyd/tests/common/` holds the
  container helpers (`container.rs`), the fake network side of the egress proxy (`egress.rs`:
  the resolver, dialer and host-address source handed to the launcher through the constructor
  seam production fills with the system resolver and TCP dialer, Task 8 decision 10, and an
  in-process echo upstream, so no packet leaves the host; no test-only code path exists in
  `sallyd`), the intercepted-TLS rig (`intercept.rs`), the redaction-form helpers (`forms.rs`),
  audit-log search (`search.rs`), run-scoped locks (`locks.rs`) and a session's built-in tools
  behind the real gate on a launched workspace (`tools.rs`). sally-core's are in
  `crates/sally-core/tests/common/`.
- **Canaries** are fixed text assembled at runtime, one per fixture secret name, and held by the
  fixture secret store, so no credential-shaped literal is in the tree; they are the same in every
  run. `canary` in `crates/sallyd/tests/common/egress.rs` holds the exact shapes: most start
  `SALLY_CANARY_`; one is a lower-case DNS label, so it can stand in a `CONNECT` host. Where a
  row names `CANARY_SECRET`, `CANARY_FILE`, `CANARY_EXEC` or a fixture (`fx-coding`,
  `fx-brokered`, `fx-chat`, `fx-wild`), it names a role: its test builds the equivalent in code.
- `tests/redteam/` also holds the syscall probe `probe/probe.c` (built into the test image at
  test time, never linked into a product binary) and the TLS clients `tls/verify.go` and
  `tls/verify.py` that check the interception CA's certificates (`crates/sallyd/tests/session_ca.rs`).
- Not built: the separate harness crate (`tests/redteam/harness/`), the fixture manifest files
  (`fixtures/manifests/`), attack scripts other than the model scripts, and a stand-alone mock
  upstream (`mock_upstream/`) that an earlier version of this section described; Task 13 in
  `docs/MILESTONES.md` names the harness.
- **Malicious mock model** (`sallyd::llm::scripted`, scripts in
  `tests/redteam/attacks/model_scripts/*.jsonl`):
  the scripted model, a `sallyd::llm::server::Backend` the test hands to the `llm.sock` server's
  constructor; deterministic replies and tool-call sequences used by RT-AG tests in CI. It is
  production code (architect Q46, Q119 on R3): one strict parser, enabled only by the explicit
  `model` param of `sessions.create`, which declares the session driven; there it is a turn
  source for `sessions.drive`, never a model a harness talks to (RT-DRV).
- Output (planned, #213): a `target/redteam/results.md` table (ID, name, PASS/FAIL, evidence
  snippet) uploaded as a CI artifact and pasted into `docs/reports/M<n>.md`. Until it exists, a
  report's table is read from the `redteam` job log of one named CI run.

Fixture roles (built in code; see above): `fx-coding` (= `coding-agent.yaml` with mock hosts),
`fx-brokered` (one `brokered` mount), `fx-chat` (= `chat-only.yaml`), `fx-wild`
(= `web-research.yaml` with `*`).

### Adding a test
1. Pick the SI it defends. 2. Add a row here with a concrete attack and a *mechanically checkable*
PASS condition. 3. Implement it as a function named `rt_<category>_<nn>_…` in the crate that owns
the defence, and add its file to the row's Test column in the order the Harness section gives. 4.
Reference the ID in the code comment of the mitigation. A mitigation without a test ID in its
comment fails review. 5. A PASS clause that asserts something absent, refused or unreachable
names its control in the row, and the control lands in the same PR as the test (#122): the same
probe, with the defence left out, finds the thing. It runs inside the same `rt_` test, before the
absence assertion, through the same probe string or scan function, and its messages start with
`control:`. Record it as "Control: `<test>` in-test (<what is left out>)"; where the hard rules
forbid leaving the defence out, as "Control (analogue): …", naming what succeeds instead and
the flag a defence-off control would need. A recorder that saw nothing (a fake resolver or
dialer, a mock upstream's log, the audit sink, a backend) records the allowed case in the same
test first. 6. Raise `REDTEAM_COUNT` in the `Makefile` by the number of `rt_` tests the PR adds:
`make redteam` fails unless exactly that many run (`scripts/redteam-guard.sh`), so a lost test file
fails the run. The count goes down only in a PR that removes a test, and its description names
every test that left; removing, renaming or ignoring an `rt_` test is the maintainer's decision.
